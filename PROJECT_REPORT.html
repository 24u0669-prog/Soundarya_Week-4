1. Executive summary

Spendwise is a personal expense-tracking application with a modern, responsive web dashboard and a Java HTTP server.

Users can create and maintain expense entries, organize them with categories, search and filter the transaction diary, and review totals and category breakdowns. In the local edition, the Java server validates requests and stores data on the user's machine. A static edition is published through GitHub Pages for demonstration; that edition stores its own data in the current browser and has no shared backend.

2. Problem and objectives

Personal purchases are easy to forget, and a list of transactions alone does not make spending patterns easy to understand. Spendwise provides one place to record expenses and a visual summary that helps a user inspect spending by date and category.

Project objectives

  • Make adding, editing, and removing an expense straightforward.
  • Summarize spending and provide a category breakdown.
  • Support search and date/category filters for the transaction history.
  • Keep the primary desktop and mobile experiences responsive and accessible.
  • Offer a locally run Java version and a clearly identified static web demo.

3. Project scope

The project covers an individual user's expense diary: expense entry and maintenance, category management, filtering, summary metrics, local persistence, and a browser-based interface. The Java server binds to the loopback interface and is intended for use on the local machine.

The GitHub Pages version demonstrates the interface and core interactions without a server. It is isolated to a browser profile and is not a multi-user finance service.

5. Application architecture

  1. Presentation: index.html defines the login screen, dashboard, expense form, and category form. styles.css provides responsive layouts and visual styling. app.js handles rendering and user actions.
  2. Application/API: ExpenseTrackerServer.java serves the frontend and exposes authentication, dashboard, expense, and category endpoints as JSON.
  3. Business/data layer: server-side logic validates expense and category input, applies filters, calculates totals, and stores data.
  4. Deployment modes: local mode uses Java APIs and the local data file; GitHub Pages mode uses browser storage through a client-side adapter.
EndpointPurpose
/api/auth/statusReports whether setup is needed and whether the current session is authenticated.
/api/auth/setup, /api/auth/login, /api/auth/logoutSet up the local diary password, start a session, or lock the diary.
/api/dashboardReturns filtered entries, spending summaries, and category totals.
/api/expensesCreates, updates, and deletes expense records.
/api/categoriesCreates and removes expense categories.

6. Implemented features

  • Overview of total spending, current-month spending, transaction count, and category count.
  • Category spending visualization with totals and proportional indicators.
  • Create, edit, and delete expenses with description, amount, category, date, and optional time.
  • Search transactions and filter by category or date range; clear filters in one action.
  • Create and manage categories; categories in use cannot be removed.
  • Local login/setup flow with password visibility controls and a lock action.
  • Responsive dashboard and login experience, with keyboard focus styles and reduced-motion support.
  • Clear validation feedback and status messages for user actions.

7. Data model and validation

An expense record contains an identifier, ISO-formatted date, optional time, positive amount, category, and description. Categories are stored separately and each saved expense must reference an existing category.

The Java implementation checks date/time formats, requires positive amounts with at most two decimal places, limits text lengths, checks category membership, and rejects an inverted date range. Local data is written through a temporary file and replaced atomically where the file system supports it.

Currency formatting is set to INR. The transaction diary includes date and time grouping to make the list easier to scan.

8. Security and privacy

Local Java edition: the server binds to 127.0.0.1. The account password is stored as a salted PBKDF2-HMAC-SHA-256 derived value (310,000 iterations, 256-bit output) in a separate local credentials file. Sessions use a random token in an HttpOnly, SameSite=Strict cookie with a 12-hour expiry.

GitHub Pages warning: a static website cannot run the Java server. The hosted demo keeps a password hash and expense data in browser storage, which is not secure authentication and does not protect data from someone with access to that browser. Do not use the public demo for sensitive financial information.

The Pages demo does not upload expense entries to the repository or share them with other visitors; browser storage is local to the visitor's browser profile. Clearing that browser's site data can remove the demo data.

9. Deployment and usage

Run the local Java application

  1. Install JDK 21 or newer.
  2. From the project root, compile and start the server:

javac -d out src\main\java\com\expense\tracker\ExpenseTrackerServer.java

java -cp out com.expense.tracker.ExpenseTrackerServer

Open http://localhost:8080. By default, the local data file is stored in the user's application data directory. The expense.data Java property or EXPENSE_TRACKER_DATA environment variable can select a different path.

Open the public demonstration

Spendwise GitHub Pages dashboard. The Pages deployment publishes static frontend files from the repository's main branch; it does not host the Java API.

10. Testing and verification

  • The Java server was compiled with JDK 25, and the local server and dashboard were launched for browser verification.
  • The login page, password visibility/reset behavior, dashboard rendering, and responsive layouts were checked in the browser.
  • The GitHub Pages deployment for commit efa88d1 completed successfully, and the hosted dashboard was verified to load.
  • The repository also contains Python unit tests for the retained legacy console tracker. Those tests cover persistence, category operations, filters, edits/deletions, and invalid input; they are not a Java web-server test suite.

Dedicated automated tests for the Java API and static Pages storage adapter are recommended as a next quality step.

11. Known limitations

  • The Java edition is a single-user, local application; it does not provide remote access, cloud synchronization, or shared accounts.
  • The Pages demo's browser-local password is only a convenience gate and is not a security boundary.
  • Demo data is separate per browser and device, with no server-side backup or synchronization.
  • Budgets, recurring transactions, export/report generation from transaction records, and multi-currency support are not part of the current implementation.
  • The project has a legacy Python test suite, but does not yet provide equivalent automated coverage for the Java application.

12. Future enhancements

  • Add automated Java API and browser end-to-end tests.
  • If shared online access is required, add a properly hosted backend, user authorization, and secure database rather than extending static browser storage.
  • Add CSV export, monthly budgets, recurring expenses, and optional charts over longer time periods.
  • Provide a guided data backup and restore workflow for the local edition.

13. Conclusion

Spendwise brings everyday expense entry and review into a clean dashboard, while keeping the local Java edition independent of third-party runtime services. The GitHub Pages edition makes the interface easy to access as a demo, with an explicit distinction between browser-only storage and the password-protected local application. The foundation is suitable for continued development, especially automated testing and a secure hosted backend if multi-device access becomes a requirement.
